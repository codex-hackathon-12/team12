# 커밋 정책

## 1. 목적

이 문서는 `develop` 브랜치의 커밋 메시지와 커밋 단위를 일관되게 유지하기 위한 기준이다. 모든 커밋은 이 정책과 `AGENTS.md`의 Git 작업 권한을 함께 따라야 한다.

## 2. 커밋 메시지 8가지 규칙

1. 제목과 본문은 빈 행으로 구분한다.
2. Header 전체는 공백을 포함해 50자 이내로 작성한다.
3. 제목은 첫 단어부터 명확하게 시작한다. 영문 고유명사로 시작할 때는 첫 글자를 대문자로 작성한다.
4. 제목 끝에는 마침표를 넣지 않는다.
5. 제목은 과거형을 사용하지 않고 현재형의 명령 의미로 작성한다.
6. 본문의 각 행은 공백을 포함해 72자 이내로 작성한다.
7. 구현 방법보다는 무엇을 변경했고 왜 변경했는지 설명한다.
8. 제목과 본문은 반드시 한글로 작성한다.

`feat`, `frontend` 같은 타입·스코프 식별자, 파일명, 코드, 제품명과 이슈 참조 키워드는 한글 작성 규칙의 예외다.

한글 제목에서는 영문과 같은 대소문자 구분이 없으므로 3번 규칙을 억지로 적용하지 않는다. 제목이 GitHub, REST API처럼 영문 고유명사로 시작할 때만 올바른 대소문자를 사용한다.

## 3. 커밋 메시지 구조

Header, Body, Footer는 각각 한 줄의 빈 행으로 구분한다.

```text
타입(스코프): 제목

본문

바닥글
```

- Header는 필수다.
- Scope는 선택이다.
- Body는 선택이다.
- Footer는 선택이다.
- 타입 뒤와 콜론 앞에는 공백을 넣지 않는다.
- 콜론 뒤에는 공백을 하나 넣는다.

## 4. Header

형식:

```text
타입(스코프): 한글 제목
```

Scope가 없을 때:

```text
타입: 한글 제목
```

Header 전체 길이는 타입, 괄호, 스코프, 콜론과 공백을 포함해 50자 이하여야 한다.

### 타입

타입은 다음 값 중 하나만 사용한다.

| 타입 | 사용 기준 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `build` | 빌드 설정, 모듈 설치 또는 삭제 |
| `chore` | 기능과 무관한 자잘한 유지보수 |
| `ci` | CI 설정 또는 스크립트 변경 |
| `docs` | 문서 추가 또는 수정 |
| `style` | 동작 변화 없는 코드 스타일과 포맷 수정 |
| `refactor` | 기능 변화 없는 코드 구조 개선 |
| `test` | 테스트 추가 또는 수정 |
| `perf` | 성능 개선 |

### Scope

Scope는 변경 영역이 분명할 때만 사용한다. 필요 이상으로 새로운 Scope를 만들지 않는다.

권장 Scope:

| Scope | 영역 |
| --- | --- |
| `frontend` | 화면, 컴포넌트와 프론트 상태 |
| `api` | REST endpoint와 서버 응답 |
| `auth` | GitHub 로그인과 세션 |
| `db` | DB 스키마와 쿼리 |
| `contract` | 공유 API 데이터 계약 |
| `billing` | mock 결제와 크레딧 |
| `gallery` | 갤러리 |
| `config` | 프로젝트 설정 |
| `test` | 테스트 기반 또는 테스트 도구 |

### 제목

- 변경사항을 한 문장으로 요약한다.
- `추가`, `수정`, `제거`, `분리`, `개선`, `방지`처럼 행동이 드러나는 현재형 표현을 사용한다.
- `추가함`, `수정했음`, `변경했다` 같은 과거형을 사용하지 않는다.
- 제목 끝에 `.`, `!`, `?`를 붙이지 않는다.
- `수정`, `업데이트`, `작업`처럼 대상이 불분명한 제목은 사용하지 않는다.

좋은 예:

```text
feat(frontend): 저장소 선택 화면 추가
fix(api): 생성 상태 응답 누락 방지
docs(contract): 갤러리 응답 형식 명시
refactor(auth): GitHub 세션 검증 로직 분리
```

나쁜 예:

```text
feat: 작업함.
fix: 버그 수정
chore: 여러 파일 업데이트
feat(frontend): 저장소 화면을 추가했습니다
```

## 5. Body

Header만으로 무엇과 왜가 충분히 설명되면 Body를 생략할 수 있다. 다음 중 하나라도 해당하면 Body를 작성한다.

- 변경 이유가 제목만으로 드러나지 않는다.
- 둘 이상의 관련 변경이 포함된다.
- 기존 동작이나 제약조건을 설명해야 한다.
- API, 데이터 구조 또는 사용자 흐름에 영향이 있다.
- 의도적으로 구현하지 않은 범위를 알려야 한다.

작성 규칙:

- Header와 Body 사이에 빈 행을 하나 둔다.
- 각 행은 72자 이내로 줄바꿈한다.
- 코드가 어떻게 동작하는지 나열하기보다 변경한 대상과 이유를 설명한다.
- 현재형으로 작성한다.
- 여러 항목이 필요하면 `-` 목록을 사용할 수 있다.

예시:

```text
feat(frontend): 저장소 선택 화면 추가

사용자가 GitHub 저장소를 검색하고 생성 대상을 선택할 수 있도록
저장소 목록, 필터와 빈 상태를 추가한다.

백엔드 통합 전에는 공유 계약을 만족하는 mock 응답을 사용한다.
```

## 6. Footer

Footer는 이슈, 작업 항목 또는 관련 문서를 참조할 때 사용한다. Body와 Footer 사이에 빈 행을 하나 둔다.

예시:

```text
Issues #1234
```

여러 참조가 있다면 한 줄에 하나씩 작성한다.

```text
Issues #1234
Issues #1250
```

관련 이슈가 없다면 Footer를 생략한다. 존재하지 않는 이슈 번호를 임의로 작성하지 않는다.

## 7. 전체 예시

기능 추가:

```text
feat(frontend): 포트폴리오 생성 진행 화면 추가

생성 작업이 끝날 때까지 사용자가 현재 단계를 확인할 수 있도록
계약에 정의된 상태를 사용하는 진행 화면을 추가한다.

백엔드 통합 전에는 동일한 DTO의 mock adapter를 사용한다.

Issues #1234
```

버그 수정:

```text
fix(api): 완료 응답의 포트폴리오 식별자 보장

완료 상태인데 portfolioId가 없는 응답으로 화면 이동이 실패하는
문제를 방지한다.
```

문서 변경:

```text
docs: 커밋 메시지 정책 추가

여러 작업자가 같은 develop 브랜치에서 일관된 형식으로 변경
이력을 남길 수 있도록 메시지 작성 기준을 문서화한다.
```

## 8. 커밋 단위

- 하나의 커밋에는 하나의 논리적 변경만 포함한다.
- 프론트엔드, 백엔드, 계약과 문서 변경을 가능한 한 분리한다.
- API 계약을 변경할 때는 계약 커밋을 구현 커밋보다 먼저 만든다.
- 의존성 변경은 `package.json`과 lockfile을 같은 커밋에 포함한다.
- 관계없는 포맷 변경을 기능 커밋에 섞지 않는다.
- 빌드 결과, 로그, 비밀 정보와 개인 환경 파일을 커밋하지 않는다.
- 미완성 코드나 실패한 검증을 완료된 기능처럼 커밋하지 않는다.

## 9. 커밋 전 확인 목록

- [ ] 통합 담당자가 수행하는 커밋인가
- [ ] 담당 영역 밖의 변경이 섞이지 않았는가
- [ ] 하나의 논리적 변경만 포함하는가
- [ ] 파일 경로를 명시적으로 stage했는가
- [ ] 타입이 허용 목록에 포함되는가
- [ ] Header 전체가 50자 이내인가
- [ ] 제목이 한글이고 과거형이나 마침표를 사용하지 않았는가
- [ ] Header와 Body 사이에 빈 행이 있는가
- [ ] Body 각 행이 72자 이내인가
- [ ] 무엇과 왜를 설명하는가
- [ ] 관련 이슈가 있을 때만 Footer를 작성했는가
- [ ] 관련 검증을 통과했는가

## 10. 금지 예시

```text
update
fix bug
feat: 기능 추가함.
chore: 이것저것 수정
feat(frontend): Added dashboard
```

다음 Git 작업도 금지한다.

- `git add .` 또는 `git add -A`
- `git push --force`
- `git push --force-with-lease`
- `git reset --hard`
- 다른 담당자의 변경을 임의로 amend, revert 또는 squash
