# Codex 대화 이력

## 문서 목적

이 문서는 2026년 8월 16일 folio.ai MVP를 만들며 사용자와 Codex가 나눈
대화를 프로젝트 의사결정 관점에서 정리한 기록이다. 대화 원문이나 Codex의
내부 추론을 옮긴 transcript가 아니라, 사용자의 요청을 정제하고 실제 결정,
변경 결과와 남은 과제를 연결한 handoff 문서다.

비밀 키, OAuth token, cookie와 로컬 환경 변수 값은 기록하지 않는다. 임시
스크린샷의 로컬 경로도 재사용 가치가 없어 생략하고 화면에서 지적된 내용만
문장으로 보존한다.

## 1. 제품 목표와 MVP 범위 확정

### 사용자 요청

- 취업생을 위한 포트폴리오와 이력서 생성 AI를 Next.js로 구현한다.
- 약 4시간 30분 안에 MVP를 완성할 수 있는 구조로 시작한다.
- Git 저장소, 사용자 프롬프트와 선택 문서를 생성 입력으로 고려한다.
- 신규 사용자에게 100크레딧을 표시하고 저장소 하나당 30크레딧을 사용한다.

### 정제된 결정

- 서비스명은 `folio.ai`로 사용한다.
- 로그인은 GitHub OAuth 하나로 고정한다.
- MVP의 크레딧과 결제는 화면·API 시연만 제공하며 실제 차감이나 승인을
  수행하지 않는다.
- 생성 결과는 포트폴리오 웹페이지와 PDF 이력서 초안을 목표로 한다.
- 초기에는 하나의 포트폴리오 스타일만 제공하고 다중 스타일과 편집기는
  후속 범위로 둔다.

### 결과

- Next.js App Router, TypeScript와 기본 개발 도구로 프로젝트를 구성했다.
- 프론트, REST API, 인증, DB, 생성 Workflow와 mock 결제까지 확장할 수 있는
  단일 저장소 구조를 선택했다.

## 2. 프론트엔드·백엔드 협업 방식 정의

### 사용자 요청

- 프론트엔드와 백엔드가 같은 `develop` 브랜치에서 병렬 작업한다.
- 서로 건드리면 안 되는 파일, commit과 push 정책을 프롬프트로 정리한다.
- 백엔드 개발 중에는 프론트가 사전 정의된 스키마에 맞춘 mock 데이터를
  사용하고 나중에 API 연결만 교체할 수 있어야 한다.

### 정제된 결정

- `AGENTS.md`에서 역할별 수정 가능·금지 경로를 정의했다.
- 공유 파일은 통합 담당자 한 명이 수정하고 Git 작업도 직렬로 처리한다.
- 모든 구현은 `architecture.md`를 단일 기준으로 따른다.
- `contracts/api-contract.ts`를 프론트와 백의 공용 DTO 기준으로 사용한다.
- UI는 `lib/api-client`만 의존하고 mock·HTTP adapter를 직접 import하지 않는다.
- 백엔드가 미완성인 동안 mock fixture가 계약 타입을 만족하도록 컴파일 단계에서
  검사한다.

### 결과

- [협업 정책](../AGENTS.md), [아키텍처](../architecture.md),
  [API 계약](api-contract.md)과 [커밋 정책](commit-policy.md)을 만들었다.
- 프론트·백 작업 로그를 분리해 같은 로그 상단을 동시에 수정하던 충돌 원인을
  제거했다.

## 3. 화면·데이터 아키텍처 구체화

### 사용자 요청

- 대시보드를 main 화면으로 두고 저장소 선택, 결제와 갤러리로 나눈다.
- 저장소 선택 후 프롬프트 입력, 대기 화면, 결과 생성 순서로 구현한다.
- 갤러리는 완성 포트폴리오 예시를 그리드로 보여준다.
- 대시보드는 로그인, 맛보기, 진입점, 공지와 이벤트로 구성한다.
- 각 기능에서 주고받을 데이터 형식을 정의한다.

### 정제된 결정

- 공개 랜딩과 로그인 대시보드를 분리했다.
- 로그인하지 않은 사용자는 `/`, 로그인 사용자는 `/dashboard`를 기본
  진입점으로 사용한다.
- 생성 작업은 `queued`부터 `completed` 또는 `failed`까지 비동기 상태를
  가지며 프론트가 2초 간격으로 polling한다.
- REST API는 `/api/v1`, camelCase JSON과 공통 성공·실패 envelope를 사용한다.
- 공개 랜딩·맛보기·갤러리·공지는 비로그인 접근을 허용하고 저장소와 결과는
  사용자 인증을 요구한다.

### 결과

- 화면 라우트, 생성 sequence, API endpoint, DTO와 오류 코드가 문서화됐다.
- 대시보드, 저장소, 생성, 결과, 결제, 갤러리와 공지의 주요 상태를 정의했다.

## 4. 커밋과 로그 정책 정리

### 사용자 요청

- 제목·본문 구분, 50자 제목, 72자 본문과 한글 작성 규칙을 포함한 커밋
  정책을 문서화한다.
- 요청 사항은 원문보다 정제된 형태로 상세 작업 로그에 계속 남긴다.
- 프론트와 백 로그 충돌을 방지한다.

### 정제된 결정

- 한글 Conventional Commits 형식을 사용한다.
- `feat`, `fix`, `build`, `chore`, `ci`, `docs`, `style`, `refactor`,
  `test`, `perf`만 commit type으로 허용한다.
- 작업 로그는 정제된 요청, 제약조건, 결정, 반영 내용, 검증과 남은 항목을
  기록한다.
- 프론트, 백, 통합 로그를 각각 별도 파일로 관리한다.

### 결과

- `docs/commit-policy.md`와 역할별 작업 로그 체계가 저장소 정책으로 정착됐다.

## 5. 프론트엔드 MVP와 퍼블리싱

### 사용자 요청

- 기능 연결 전에 디자인 피드백이 가능하도록 퍼블리싱을 먼저 완성한다.
- 로컬 터미널에서 직접 화면을 확인할 수 있어야 한다.
- 전체 글꼴을 Pretendard로 바꾸고 제목 굵기, 본문 크기와 부자연스러운
  줄바꿈을 개선한다.

### 진행 중 발생한 문제

- 로컬 개발 서버에서 `DashboardShell.tsx` 동적 module import가 실패했다.
- 원격 `develop`이 앞서 있어 non-fast-forward push가 거절됐다.

### 결과

- 모듈 로딩 문제를 복구하고 전체 MVP 화면을 퍼블리싱했다.
- Pretendard WOFF2 굵기 9개를 `@font-face`로 등록하고 전역 글꼴로 적용했다.
- 큰 제목의 굵기를 낮추고 본문 크기, 행간, `word-break`와 반응형 폭을
  조정했다.
- push 전 fetch·rebase·검증 순서를 적용해 원격 변경을 보존했다.

## 6. 페이지별 디자인 피드백 반영

### 공개 랜딩과 대시보드

- 랜딩 hero와 맛보기는 로그인 전 `/`에만 노출한다.
- 로그인 사용자가 `/`에 접근하면 `/dashboard`로 바로 이동한다.
- 랜딩의 `대시보드` 문구는 인증 의미가 분명한 GitHub 로그인 CTA로
  통일한다.
- 대시보드에서는 최근 작업·공지 영역을 먼저, 크레딧 현황을 그 아래에
  배치한다.

### 포트폴리오 만들기

- 저장소를 여러 개 선택할 수 있는 UI를 제공한다.
- 저장소 선택 화면의 과도한 대제목과 GitHub 연결 계정 카드를 제거한다.
- 선택 요약 바는 화면을 따라다니는 sticky 요소가 아니라 저장소 목록 아래의
  일반 콘텐츠로 배치한다.
- 다중 선택 ID는 mock 시연에 사용하되 HTTP 생성 요청은 합의된 대표
  `repositoryId` 계약을 유지한다.

### 결과·갤러리·크레딧

- 결과 포트폴리오는 갤러리의 정적 예시와 별도 variant로 구성한다.
- 갤러리 디자인은 유지한다.
- 크레딧 페이지의 중복 mock 안내 섹션을 제거하고 상품 영역의 설명만
  유지한다.

### 결과

- 공개 랜딩, 개인 대시보드와 생성 흐름의 역할이 분명해졌다.
- 디자인 변경은 desktop, tablet과 mobile breakpoint에 함께 반영됐다.

## 7. Figma와 디자인 전달 방식 논의

### 사용자 질문

- `.fig` 파일을 직접 읽을 수 있는지, MCP를 연결하면 가능한지 확인했다.

### 답변과 상태

- `.fig` 원본 파일만으로는 구조를 안정적으로 해석하기 어렵고 Figma MCP나
  공유 링크, frame 정보가 있으면 디자인 구조와 속성 확인이 수월하다고
  안내했다.
- 현재 저장소 작업에서는 Figma plugin 연결이나 `.fig` import를 실제로
  수행하지 않았다.

## 8. 백엔드 확인과 REST API 연결

### 사용자 요청

- 현재 백엔드 설정을 확인하고 남아 있는 API를 고려한 연결 계획을 세운 뒤
  바로 연동한다.

### 정제된 결정

- UI가 사용하는 `ApiClient` interface는 유지하고 HTTP adapter만 강화한다.
- `NEXT_PUBLIC_API_MODE=http`일 때 실제 `/api/v1` Route Handler를 호출한다.
- 비 JSON 응답, 네트워크 실패, 잘못된 envelope와 API 오류를 구분한다.
- 서버의 `x-request-id`를 프론트 오류 객체에 보존한다.
- 보호 API의 `401`은 현재 경로를 `returnTo`로 보존해 GitHub 로그인으로
  연결한다.

### 확인 결과

- 공개 API의 정상 응답과 보호 API의 인증 오류 응답을 확인했다.
- GitHub callback에서 `AUTH_FAILED`가 표시된 사례는 UI 문제가 아니라 실제
  OAuth·Supabase 설정 또는 migration을 함께 확인해야 하는 통합 이슈로
  분류했다.

### 남은 확인

- 실제 GitHub OAuth 완료 후 저장소 동기화부터 생성 결과까지 end-to-end 검증
- 배포 환경의 callback URL과 Supabase migration 확인
- 실제 생성 결과와 private PDF 다운로드 검증

## 9. 화면 녹화용 mock 브랜치

### 사용자 요청

- 실제 API 설정과 무관하게 모든 UI가 동작하는 것처럼 녹화할 수 있도록
  별도 브랜치에서 mock 흐름을 준비한다.
- 기존 `develop`의 API 연결 작업은 먼저 push하고 그대로 보존한다.

### 결과

- REST 연결 보강을 `develop`에 반영했다.
- `codex/demo-recording` 브랜치에 mock 기반 화면 녹화 흐름을 분리했다.
- 녹화 전용 변경이 실제 통합 브랜치의 HTTP 연결을 덮어쓰지 않도록 했다.

## 10. 완성 포트폴리오 디자인 확장

### 사용자 요청

- 기존 결과가 너무 간결하고 실제 포트폴리오처럼 보이지 않으므로
  `develop`의 완성 디자인을 확장한다.

### 정제된 결정

- 갤러리 예시의 기존 디자인은 유지하고 소유자 결과 페이지의 `result`
  variant만 변경한다.
- 단순 결과 보고서가 아니라 지원자가 실제로 공개할 수 있는 개인 사이트의
  정보 구조를 사용한다.

### 결과

- 포트폴리오 내부 navigation, 프로필 hero와 핵심 지표를 추가했다.
- About, 프로젝트별 Challenge·Approach·Impact와 highlight를 구성했다.
- 기술 그룹, 언어 비율, Git 패턴을 묶은 Expertise 섹션을 추가했다.
- Contact CTA, footer, mobile·tablet·print 레이아웃을 완성했다.
- ESLint와 production build를 통과하고 `develop`에 반영했다.
